## 两种叙事模式

- **数字牌 ACE—X（10张×4组）**：以**原著向读者揭示事件的顺序**讲连续故事；兼容传统塔罗正逆位和数字牌的基本含义。原著没有杯、权杖、剑、星币这些道具时，明确标记为塔罗原创象征。
- **宫廷牌 PAGE / KNIGHT / QUEEN / KING（4张×4组）**：同一部原著的关键人物或核心存在，是**人物/力量档案**；宫廷称谓是塔罗功能原型，不是原著中的头衔，也不必都有人类外形。应有**人类→混血/变异→异族→宇宙存在**等实质形态变化，不能全部画成贵族。
- **圣杯特例**：完整显出鱼人/深潜者化的视觉进程；原著结局是叙述者**计划**前往Y'ha-nthlei，展示完整的实际变身或归海场面属于原创延伸，必须标注。

## 风格统一（不接受泛奇幻替代）

- 画幅 9:16；**固定复用现有大阿卡纳定稿黑金古董边框**，上下浅色旧羊皮纸铭牌，顶部 ACE / 罗马数字 / PAGE / KNIGHT / QUEEN / KING，底部英文大写标题，不在原画写中文。
- 内部采用克苏鲁原著的时代、地点、人物、研究工具、建筑与生态，不准用“红披风骑士＋魔法城堡＋日蚀”反复替代故事。
- 画面既有静谧、迷惑、眷恋、哀伤与恐惧，也有非人造型；不要所有牌都堆叠巨大怪物、触手和古堡。
- 一张牌有一个清晰主行动和叙事焦点；非欧几里得/不可名状元素尽量通过环境、尺度、纹理和光学反常表现。
- 数字牌花色符号**必须刚好等于数字**（含背景、手持、反射、额外摆件）；如真实场景不适合堆十把剑，先明确统一的边框符号计数方案，**不得既在画内又在边框重复计数**。宫廷牌重视本花色主象征，无数字计数义务。
- 不能从用户确认的已定稿大阿卡纳中擅自改变外观。新图按张呈现，避免多卡拼图；数量、英文牌名和边框一致性逐张校验。

## 工作方式 / 不能跳过的关卡

1. **G0 底稿检查**：读取 `56-cards-spec.md`、`56-cards-data.json`，核对四篇原著、传统塔罗含义、人物和物种；逐张修正历史瑕疵。
2. **G1 风格锁定**：从仓库读取已确认的原画及牌框，明确边框固定资产/排版；不从记忆擅造相似框。
3. **G2 叙事样卡**：圣杯二、圣杯五、圣杯十优先试制，三张分别测试关系、失落与异化归属；用户明确确认后，再扩展到该组。
4. **G3 56张逐张制作**：按每组原著时间顺序推进；一张一图、独立内容、精确数符号、角色物种合理、审图记录。
5. **G4 网站集成**：只有经确认的图片才进最终牌库；保持大阿卡纳原样；小阿卡纳遵循现有“牌库+独立详情页+抽牌池”交互标准，不能把生产审核台账当成用户界面。
6. **G5 线上验证**：原图和缩略图完整、正确牌名/数量、手机端无溢出、56牌可访问、78牌总数正确、旧大阿卡纳无回归问题。

### 已经验证的图片上线流程（必须优先复用）

1. 新图在工作空间经确认且可读；
2. Google Docs/Drive 图片临时接力，以得到可由 GitHub Actions 读取的图片地址；
3. GitHub Actions 下载原图并转**无损 WebP**，生成高清版与缩略图，逐像素核对，推送 `gh-pages`；
4. 更新站点资产清单、牌库数据、详情路由、缓存版本和抽牌池；
5. 对线上真实 URL 进行浏览器/移动端 QA，通过后汇报实际链接；
6. 清理临时文档、一次性 Actions 工作流。

**不要再把 GitHub 图片上传判断为“不可能”**；曾经验证成功。若工具失败，先找已验证的替代路径，不能在尚未检查时声称无法发布。
